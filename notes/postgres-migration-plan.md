# Postgres Migration Plan — fetchr

## Context

fetchr is currently backed by SQLite (`sqlite:///fetchr.db`). The expansion plan
calls for Postgres as the first step toward a commercial-scale matching platform
because:

- SQLite deadlocks under parallel scraper workers
- Postgres `JSONB` enables GIN indexing for ML feature queries (e.g. "dogs whose
  `personality_traits` contains 'energetic'")
- PostGIS and `pgvector` (future) require Postgres
- The matching platform needs a queryable network service, not a local file

This migration is **schema-only** — the 100-dog SQLite dataset will be re-scraped.
No data migration is needed.

## Step-by-Step Changes

### 1. `requirements.txt`


**Why `psycopg2-binary`:** bundles its own libpq — no system Postgres client
library needed. Fine for dev/CI. Swap to `psycopg2` in a Dockerfile for a
smaller image.

**Why Alembic:** `Base.metadata.create_all()` is for greenfield only. Alembic
tracks schema changes as versioned scripts so future column additions have an
upgrade path.

### 3. `db/connection.py`

**Import change:** swap `DB_PATH` for `DATABASE_URL`.

**Engine replacement:**

Remove:
```python
engine = create_engine(
    f"sqlite:///{DB_PATH}",
    connect_args={"check_same_thread": False},
)
```

Replace with:
```python
engine = create_engine(
    DATABASE_URL,
    pool_pre_ping=True,   # detect stale connections before handing them out
    pool_size=5,          # baseline connections kept alive between scrape runs
    max_overflow=10,      # burst capacity for parallel future workers
)
```

**Why `pool_pre_ping=True`:** Postgres connections go stale when the scraper
idles between detail-page fetches (2–5s delays × hundreds of dogs). Without it,
a dead connection is handed to `upsert_dog()` and fails. With it, SQLAlchemy
issues a cheap `SELECT 1` first and reconnects transparently.

**Why `check_same_thread=False` is removed:** That flag is SQLite-specific. It
disables SQLite's single-thread safety check. Postgres uses per-connection
pooling — no equivalent flag exists or is needed.

**`create_tables()` — remove it from the startup path entirely.**

Once Alembic is wired up, `create_tables()` calling `Base.metadata.create_all(engine)`
becomes a maintenance hazard. If `main.py` calls it on startup and the database is
empty (e.g. a new dev machine), SQLAlchemy creates the tables directly from the ORM
models — bypassing Alembic's version tracking. Now `alembic_version` is empty but the
tables exist. Any subsequent `alembic upgrade head` either fails with "table already
exists" or applies migrations on top of a half-tracked schema, producing a confusing
and hard-to-unwind state.

The fix: remove `create_tables()` from `main.py`'s startup call. `alembic upgrade head`
is the only schema initialization path from this point forward. `create_tables()` itself
can stay in `db/connection.py` but should be used only from `tests/test_upsert_dog.py`,
which calls it explicitly against its own in-memory SQLite engine.

**Everything else in `db/connection.py` is unchanged:** `upsert_dog()`,
`_LIVE_FIELDS`, `_has_live_changes()`, `_archive_snapshot()`, `save_raw_scrape()`,
`export_to_json()` — all use SQLAlchemy ORM calls that are dialect-agnostic.

### 4. `models/dog.py` — JSON → JSONB

**Import change:** add `from sqlalchemy.dialects.postgresql import JSONB`.

**11 columns to change** (in `DogORM`, `DogProfileHistory`, and `RawScrape`):

In `DogORM`:
- `personality_traits`
- `org_social_urls`
- `org_special_services`
- `photos`
- `media_records`
- `tags`

In `DogProfileHistory`:
- `photos`
- `media_records`
- `tags`
- `personality_traits`

In `RawScrape`:
- `raw_json`

**Why `RawScrape.raw_json` must also be JSONB — not plain JSON:**

The original plan listed 10 columns and missed this one. `raw_json` stores the entire
`__NEXT_DATA__` blob from PetFinder — the full nested JSON object before any normalization
happens. This is the richest JSON document in the entire schema: it contains every field
PetFinder has ever sent, including fields we haven't mapped to `dog_profiles` columns yet.

With plain `JSON`, Postgres stores it as raw text and re-parses the string on every query.
With `JSONB`, Postgres stores a binary parse tree and a GIN index can be built on it.
This matters because `raw_scrapes` will grow to tens of thousands of rows (one row per
scrape run per dog), and these are exactly the queries you'll want to run:

```sql
-- Detect schema drift: what top-level keys has PetFinder added that we're not capturing?
SELECT DISTINCT jsonb_object_keys(raw_json->'props'->'pageProps'->'animal')
FROM raw_scrapes;

-- Find all raw scrapes where PetFinder added a new 'behaviorScore' key
SELECT source_id, scraped_at
FROM raw_scrapes
WHERE raw_json->'props'->'pageProps'->'animal' ? 'behaviorScore';

-- Reconstruct the full adoption status timeline for a dog from raw blobs
SELECT scraped_at, raw_json #>> '{props,pageProps,animal,residency,adoptionStatus}'
FROM raw_scrapes
WHERE source_id = '12345678'
ORDER BY scraped_at;
```

None of these queries are practical at scale against a TEXT column. `raw_scrapes` is the
audit trail and schema drift detector — it has the strongest case for JSONB of any table.

**From:** `Column(JSON, default=list, nullable=False)`
**To:** `Column(JSONB, default=list, nullable=False)`

**Why `JSONB` and not `JSON`:** Postgres stores `JSON` as raw text, re-parsed on
every read. `JSONB` stores a binary parse tree and supports GIN indexes — the ML
query "find dogs where `personality_traits` contains 'energetic'" can use an index
instead of a full table scan. This is exactly the query pattern the matching
platform needs.

**SQLite test compatibility:** `JSONB` is defined in
`sqlalchemy.dialects.postgresql` but inherits from SQLAlchemy's base `JSON` type.
When SQLAlchemy creates a table against a SQLite dialect, it calls
`type_.dialect_impl(dialect)` on each column type. Since `JSONB` subclasses
`JSON`, SQLite falls back to the `JSON` implementation (TEXT storage). The
in-memory SQLite tests in `tests/test_upsert_dog.py` will continue to pass
unchanged.

### 4b. `models/dog.py` — `DateTime` → `DateTime(timezone=True)`

**Import change:** SQLAlchemy's `DateTime` accepts a `timezone` parameter — no new import needed.

**What to change:** every `Column(DateTime, ...)` in all three ORM models.

In `DogORM` (8 columns):
- `birth_date`, `adoption_date`, `adoption_status_change_date`, `intake_date`
- `transfer_date`, `listed_at`, `first_seen_at`, `last_updated_at`

In `DogProfileHistory` (2 columns):
- `archived_at`, `listed_at`

In `RawScrape` (1 column):
- `scraped_at`

**From:** `Column(DateTime, nullable=...)`
**To:** `Column(DateTime(timezone=True), nullable=...)`

**Why this matters:** SQLAlchemy's plain `DateTime` maps to Postgres
`TIMESTAMP WITHOUT TIME ZONE`. When your application writes a timezone-aware
Python datetime (e.g. `datetime.now(timezone.utc)`), Postgres silently strips
the `+00:00` on insert — it stores the numbers but loses the timezone context.
This works fine while everything is UTC, but breaks the moment you run queries
that mix `NOW()` (which Postgres evaluates in the server's local timezone) with
stored timestamps. `TIMESTAMPTZ` (`DateTime(timezone=True)`) stores UTC
internally and converts on read — it's timezone-correct by construction.

The current codebase is already inconsistent: `save_raw_scrape()` does
`.replace(tzinfo=None)` to strip timezone info before writing, which is a
workaround for this exact problem. Switching to `TIMESTAMPTZ` removes the need
for that workaround.

**SQLite compatibility:** SQLite stores everything as text regardless. The
`timezone=True` flag is a Postgres-only instruction and is silently ignored by
the SQLite dialect. In-memory test behavior is unchanged.

## One Thing to Flag: Soft FK on `dog_profile_history`

The current `DogProfileHistory` model has this comment:
> "soft FK to dog_profiles.id (no DB-level constraint so SQLite doesn't need
> foreign-key pragma to be enabled)"

With Postgres, a real `ForeignKey` constraint is possible and desirable — it
catches bugs where history rows reference profiles that were deleted. However,
adding it to the ORM model would break SQLite tests (SQLite has FK pragma disabled
by default). **Recommendation:** leave the ORM model as-is (soft FK), but add the
FK constraint as a manual `op.create_foreign_key(...)` call in the Alembic
migration script. This way Postgres gets the constraint and SQLite tests are
unaffected.
