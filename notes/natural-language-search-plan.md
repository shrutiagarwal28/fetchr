# Plan: Natural-language dog search UI

> Status: design approved in principle (Claude-parses + Streamlit). This revision
> raises it to staff-level: sharper contracts, the personality-matching fix,
> hybrid filter/rank, an LLM eval harness, error taxonomy, observability, cost
> controls, and a phased rollout.

## 1. Context & problem statement

fetchr ingests dogs into Postgres but offers no way to *query* them in plain
language. We want: type `"a calm small dog that's good with cats and already
house trained"` → get matching dogs as cards.

The core problem is **translating untrusted free text into a safe, correct DB
query**. Two failure axes to design against:
- **Safety** — user text must never reach SQL. (Injection, denial-of-wallet.)
- **Correctness** — the translation must respect the data's real semantics
  (tristate unknowns, controlled vocabularies, precision/recall tradeoffs).

Pipeline (the LLM never emits SQL — it fills a validated struct):

```
plain text ─► parser.py ─► DogQuery ─► query.py ─► (filtered + ranked rows) ─► app.py
             (Claude)      (Pydantic    (SQLAlchemy ORM)                       (Streamlit)
                            contract)
```

## 2. Design principles (the "why")

1. **`DogQuery` is an anti-corruption layer.** The LLM can only populate a fixed,
   typed, enum-constrained struct. Worst case = wrong filters, never SQL
   injection. This is the load-bearing security decision.
2. **Single source of truth for vocabulary.** DB enums, the Pydantic schema, and
   the LLM prompt must not drift. Define the controlled vocabularies *once*
   (`search/vocab.py`) and feed all three from it.
3. **Hard-filter facts; rank fuzzy preferences.** Structured attributes (size,
   age, gender, good-with, fee) are deterministic → `WHERE`. Temperament is
   fuzzy and lossy → contributes to `ORDER BY` score, not a hard `WHERE`. This is
   the difference between "0 results because the user said 'calm'" and a good
   result set. (See §4 — this is the key correctness insight.)
4. **Deterministic core, probabilistic edge.** `query.py` is pure and fully
   testable with zero network. Only `parser.py` touches the LLM, behind a
   narrow, mockable seam.
5. **Dependency injection over import-time singletons.** Pass the Anthropic
   client and DB session in; don't construct them at module import (kills
   testability and Streamlit re-run performance).

## 3. Data reality (verified against the live DB, 225 live dogs)

- Clean enums — `size` {small, medium, large, xlarge}, `age_category`
  {puppy, young, adult, senior}, `gender` {male, female}, `status`
  {available, adopted}.
- **`activity_level` is 100% NULL.** Temperament ("calm", "energetic") cannot map
  to it — it must map to `personality_traits`.
- `good_with_kids/dogs/cats`, `house_trained` are **tristate** (true / false /
  NULL=unknown). NULL = untested, not "no" (see `models/features.py` Phase-2
  notes). Coverage is partial: good_with_cats known for only 81/225,
  good_with_dogs 157/225, house_trained 147/225.
- All 225 dogs have ≥1 photo → cards can always render an image.
- `coat_length` {Short, Medium, Long, Curly, Wire, NULL}; `state` populated for
  most rows.
- **`personality_traits` is dirty free-text-ish**: dupes and casing variants
  ("Couch potato" vs "Couch Potato"), and values like "Good with Kids",
  "Housetrained" that duplicate structured columns. Must be normalized before
  use (lowercase + dedupe).

## 4. The personality-matching problem (and the fix)

**Naive design fails.** If the LLM extracts free-form keywords ("calm",
"cuddly") and we ILIKE them against `personality_traits`, almost nothing matches
— the DB says `"Couch Potato"`, `"Quiet"`, `"Gentle"`, not "calm". Strict ANDed
ILIKE filtering on fuzzy terms returns mostly empty sets. This is the #1 thing
that would make the feature feel broken.

**Fix — controlled vocabulary + hybrid scoring:**
1. **Controlled vocab.** At build time, materialize the normalized distinct trait
   set into `search/vocab.py` (regenerated by a small script, not queried live on
   every request). Constrain `DogQuery.personality_traits: list[Literal[...]]` to
   that set, and list it in the system prompt so the LLM *maps* "calm" →
   `["Couch Potato","Quiet","Gentle"]` from the real vocabulary instead of
   inventing strings. (Refresh the vocab when the trait set grows materially;
   note this as a maintenance task.)
2. **Rank, don't hard-filter.** Temperament traits become an ORDER BY score =
   count of the dog's traits that intersect the requested set. Dogs with more
   overlap rank higher; dogs with none still appear *below* the matches rather
   than vanishing. Structured filters stay as hard `WHERE` clauses.

This keeps precision on facts and recall on vibes — the right altitude.

## 5. Contracts (define these first)

```python
# search/schema.py
class DogQuery(BaseModel):
    sizes: list[SizeLiteral] = []
    age_categories: list[AgeLiteral] = []
    gender: Optional[GenderLiteral] = None
    good_with_kids: Optional[bool] = None
    good_with_dogs: Optional[bool] = None
    good_with_cats: Optional[bool] = None
    house_trained: Optional[bool] = None
    special_needs: Optional[bool] = None
    breed_contains: Optional[str] = None          # ILIKE, hard filter
    personality_traits: list[TraitLiteral] = []   # controlled vocab → ranking
    state: Optional[str] = None
    city: Optional[str] = None
    max_adoption_fee: Optional[int] = None

    def is_empty(self) -> bool: ...   # no constraints extracted at all

# search/parser.py
class ParseError(Exception): ...      # safe, user-facing message; details logged
def parse_query(text: str, *, client: Anthropic, model: str) -> DogQuery: ...

# search/query.py
@dataclass(frozen=True)
class SearchResult:
    dogs: list[DogORM]
    total_matched: int
    excluded_unknown: dict[str, int]  # e.g. {"good_with_cats": 144} for transparency
def search_dogs(session, query: DogQuery, *, limit: int = 50) -> SearchResult: ...
```

Returning a `SearchResult` (not a bare list) lets the UI show *how many* dogs a
tristate filter hid as "unknown" — honest UX, and it makes the exclude-NULL
semantics legible instead of mysterious.

## 6. Module responsibilities

### `search/vocab.py` (+ `scripts/gen_search_vocab.py`)
Single source of truth: the size/age/gender literals and the normalized trait
vocabulary. `Literal` types in `schema.py` derive from here. The generator
script reads distinct `personality_traits`, normalizes (lowercase, dedupe,
drop column-duplicating traits like "Housetrained"), and writes the list.

### `search/parser.py`
- **Input validation first** (cheap rejects before any API spend): empty →
  `ParseError`; cap length (~500 chars).
- Calls `client.messages.parse(model=model, max_tokens=512, system=SYSTEM_PROMPT,
  messages=[{"role":"user","content":text}], output_format=DogQuery)` →
  `response.parsed_output`. (`max_tokens` is small — this is extraction.)
- **Client + model injected** (DI), not constructed here.
- **Model:** default `claude-opus-4-8`; configurable via `config.SEARCH_MODEL`.
  Extraction is cheap/easy, so `claude-haiku-4-5` is a defensible cost/latency
  swap later — left as a one-line config change, not hardcoded.
- **System prompt** = factual vocabulary brief: exact enum values, the controlled
  trait list, "temperament → personality_traits (activity_level is unused)", and
  "only set a good_with_* flag when the user explicitly mentions it." Keep it
  declarative (Opus 4.8 follows literal instructions well; over-prescription
  hurts).
- **Prompt caching:** the system prompt (vocab brief) is stable and reused on
  every search → mark it with `cache_control` so repeated searches read it from
  cache (~0.1× cost) instead of reprocessing the vocabulary each time.
- **Error taxonomy** (typed, mapped to one safe `ParseError` for the UI; full
  detail + Anthropic `_request_id` logged server-side):
  - `AuthenticationError` → config problem, log + generic message.
  - `RateLimitError` / `APIStatusError(5xx)` → SDK already retries; surface
    "try again".
  - `stop_reason == "refusal"` → treat as no-result, don't read content.
  - validation error from `messages.parse` → log raw output, return empty query.

### `search/query.py`
Pure function, parameterized ORM only (no string interpolation):
- Always: `deleted_at IS NULL`, `status == "available"` (default; relaxable).
- **Empty-query guard:** if `query.is_empty()`, do *not* return all 225
  unranked — return a small recent default set and let the UI prompt for more
  detail. (Prevents the "match everything" degenerate case.)
- List filters → `.in_(...)`. Scalars → `==` / `.ilike("%v%")`.
- Tristate → only filter when set; `is_(True)` excludes NULL. Compute the
  excluded-NULL counts for `SearchResult.excluded_unknown`.
- `max_adoption_fee` → `adoption_fee <= v AND adoption_fee IS NOT NULL`.
- **Personality ranking** → score = number of requested traits present in the
  dog's normalized `personality_traits` (single SQL expression over
  `jsonb_array_elements_text`); `ORDER BY score DESC, listed_at DESC`. Keep this
  in one helper; AND-ing fuzzy traits as hard filters is explicitly rejected (see
  §4).

### `app.py` (Streamlit, repo root)
- **Cache expensive resources across re-runs** — Streamlit re-executes the whole
  script on every interaction:
  - `@st.cache_resource` for the Anthropic client and (reuse) the existing
    `Session`/engine from `db/connection.py` — never build a second engine.
  - Gate the API call behind the submit button + `st.session_state` so typing
    doesn't fire a paid parse on every keystroke/re-run.
- Flow: text input → on submit, `parse_query()` → show parsed `DogQuery` in an
  expander (transparency + debugging + teaching) → `search_dogs()` → render cards
  (photo `photos[0]`, name, breed, age, size, city/state, good-with badges, fee,
  link to `source_url`).
- Show `excluded_unknown` ("144 dogs hidden: cat-compatibility untested") and a
  friendly empty-state.

## 8. Testing & evaluation

**Unit (deterministic, no network):**
- `test_search_query.py` — highest value. Drive `search_dogs` against a session
  (SQLite in-memory or injected fake): list filters, tristate excludes NULL +
  reports counts, personality *ranking order*, empty-query guard, deleted/adopted
  excluded.
- `test_search_schema.py` — `DogQuery` rejects off-vocab (`size=["gigantic"]`,
  bogus trait), accepts valid; `is_empty()` correct.
- `test_search_parser.py` — mock the Anthropic client; assert input validation
  (empty/over-long), error-taxonomy mapping (refusal/rate-limit → `ParseError`
  or empty query), and that mocked `parsed_output` flows through.

**LLM eval harness (the staff-level addition):** `tests/eval_parser.py` — a small
golden set of `(text → expected DogQuery)` cases ("small calm dog good with
cats", "senior lab in NJ under $200", "puppy good with kids and other dogs").
Run against the real model on demand (marked `@pytest.mark.eval`, skipped in CI
by default). This is how we catch parser regressions when prompts/models change —
without it, prompt edits are unfalsifiable.

## 9. Security

- LLM output constrained by Pydantic + ORM → user text cannot reach SQL; prompt
  injection can only mis-set filters.
- Validate + length-cap input before the API call (cost + abuse / denial-of-wallet).
- `ANTHROPIC_API_KEY` via env only; never logged, never in code.
- Errors logged server-side with `_request_id`; UI shows generic messages only.
- Consider a simple per-session rate limit in the UI later (out of scope v1, but
  flagged).

## 10. Observability & cost

- **Logging:** one structured log line per search — input length (not raw PII by
  default), parsed `DogQuery`, result count, latency, Anthropic `_request_id`,
  cache-hit tokens. This doubles as the data source for growing the eval set.
- **Cost controls:** small `max_tokens`; prompt-cache the system vocab brief;
  optional in-process LRU cache keyed on normalized input text (same query →
  skip the API). Default Opus 4.8 with documented Haiku swap.

## 11. Phased rollout (each milestone independently shippable/verifiable)

- **M1 — deterministic core (no LLM):** `vocab.py`, `schema.py`, `query.py` +
  unit tests. Validate the entire DB layer by hand-constructing `DogQuery`
  objects. Zero API spend, fully green tests.
- **M2 — parser:** `parser.py` + mocked unit tests + the eval harness. Wire the
  controlled vocab + prompt caching.
- **M3 — UI:** `app.py` with resource caching and submit-gating; docs + config.

## 12. Risks & tradeoffs (explicit)

| Risk | Mitigation |
|---|---|
| Vocab drift (DB traits change) | `vocab.py` regenerated by script; refresh task noted |
| Fuzzy temperament → empty results | Rank, don't hard-filter (§4) |
| Tristate hides untested dogs silently | `excluded_unknown` surfaced in UI |
| Streamlit re-runs → repeated paid parses | `cache_resource` + submit-gating + input cache |
| Prompt/model change silently regresses parsing | golden eval set (§8) |
| Over-broad/empty query returns everything | `is_empty()` guard returns recent default + prompt |

## 13. Out of scope (future / evolutionary debt)

- Embedding-based semantic ranking (v1 is controlled-vocab + overlap score).
- Soft tristate ("prefer good-with-cats, rank unknowns lower").
- GIN index on `personality_traits` (fine at 225 rows; matters at scale).
- Pagination, auth, multi-tenant rate limiting.
- FastAPI/JSON API for the commercial product (Streamlit is the internal/demo UI).
